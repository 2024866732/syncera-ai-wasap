## ⚠️ Critical Discovery (Jul 2026) — SAP Headers NOT in Cookies

**`x-sap-ri` and `x-sap-sec` are NOT stored in browser cookies.** They are dynamically generated by JavaScript in the SPX portal client-side code for every API request. Attempting to extract them from `document.cookie` or the `Cookie` header via DevTools → Application → Cookies will **always fail**.

### What This Means

| Assumption (WRONG) | Reality |
|---|---|
| `sap_ri` is a cookie set during login | ❌ Not in cookies at all — JS generates it per request |
| `sap_sec` is a cookie set during login | ❌ Not in cookies at all — JS generates it per request |
| `_extract_sap_headers()` can find them with regex | ❌ Always returns empty dict |

### How They Actually Work

- `x-sap-ri` (~36 hex chars, UUID-like): Likely a session-scoped request identifier. **May be static per session** (same value for all requests in one login session).
- `x-sap-sec` (~500+ chars base64-like): Likely an HMAC signature or encrypted payload that includes a timestamp component. **May change per request**.
- `device-id`, `app`, `version`: **Static/hardcoded** — same across all requests in the portal build.
- Generation logic is in the SPX portal JavaScript bundle (`@servicepoint/vue-project:1.0.0-231130`).

## entity_id Mapping

- `entity_id` is NOT the tracking number (SPXMY...)
- It's the internal SPX order ID (long integer, e.g. 2607444116193438)
- **Source:** `order["id"]` from the SPX order list API (`/sp-api/point/order/collection/list`)
- SPX returns `id` as an integer → cast to string for `show_secret`
- **Already stored** in DB column `entity_id` during `upsert_spx_order()` via `str(order["id"])`

## Pilihan Approach — What to Try (Priority Order)

### Pilihan A (Current): Cookies-only, no SAP headers ⭐

Since `fetch_spx_order_list()` (the main order list API) works **without any SAP headers** using just session cookies + fixed headers (Referer, Origin, User-Agent, Accept), **try `show_secret` with the same minimal headers first**.

```python
headers = {
    "Cookie": cookies,
    "Content-Type": "application/json;charset=UTF-8",
    "Referer": "https://sp.spx.shopee.com.my/",
    "Origin": "https://sp.spx.shopee.com.my",
    "User-Agent": "Mozilla/5.0",
    "Accept": "application/json",
    "device-id": "v2-MmYeRgaFMgI2X-ZbOc_fC",
    "app": "SP Portal",
    "version": "@servicepoint/vue-project:1.0.0-231130",
}
```

**Result to check:** If `show_secret` returns `retcode: 0` with `data.real_message`, the SAP headers are NOT required — the main session cookies are sufficient. Done.

**If HTTP 401:** SAP headers are required. Move to Pilihan B or C.

### Pilihan B (Complex): Reverse-engineer JS generation

Analyze the SPX portal JavaScript to find how `x-sap-ri` and `x-sap-sec` are generated, then replicate in Python:
- Look for the function that calls `show_secret` in the JS source (search for "show_secret" in the portal's app.*.js)
- Trace back to find how `x-sap-ri` and `x-sap-sec` values are computed
- May involve HMAC, timestamp-based signing, or session-derived values
- **Time estimate:** 1-3 days of JS analysis + Python replication

### Pilihan C (Workaround): Manual paste per session

Have the user paste the `x-sap-ri` and `x-sap-sec` values from the network tab into the dashboard once per session:
- Extend `spx_session` table with `sap_ri TEXT` and `sap_sec TEXT` columns
- Add fields to the dashboard SPX session config form
- Use stored values in `fetch_spx_phone()` headers
- If values are static per session, this works. If they change per request, this fails.

## Code Implementation

### Current approach (Jul 2026)

```python
def _extract_sap_headers(cookies: str) -> dict:
    """Returns sap_ri/sap_sec from cookie string if user manually pasted
    them as sap_ri=<value>; sap_sec=<value> OR x-sap-ri=<value>; x-sap-sec=<value>
    in the session cookies field.
    Returns empty dict if not found (expected — these are JS-generated headers,
    not cookies, but users can paste from DevTools network tab)."""
    result = {}
    if not cookies:
        return result
    for name, pattern in [
        ("x-sap-ri", r'(?:x-)?sap_ri=([^;\s]+)'),
        ("x-sap-sec", r'(?:x-)?sap_sec=([^;\s]+)'),
    ]:
        m = re.search(pattern, cookies, re.I)
        if m:
            result[name] = m.group(1)
    return result
```

**Regex note:** Uses `[-_]` to match both `sap_ri` (underscore, old cookie format) AND `sap-ri` (hyphen, actual HTTP header name `x-sap-ri`). The `(?:x-)?` makes the `x-` prefix optional. Without `[-_]`, pasting `x-sap-ri=VALUE` (hyphen from DevTools) silently fails.

In `fetch_spx_phone()`:
- SAP headers are OPTIONAL — only added if found
- No warnings logged if missing (expected behavior)
- The primary `headers` dict always includes `Cookie`, `device-id`, `app`, `version`, `Content-Type`, `Referer`, `Origin`, `User-Agent`, `Accept`

## ⚠️ CRITICAL REGEX PITFALL (Jul 2026) — `x-` prefix MUST be optional

**Root cause of 25 missing phones (Jul 2026):** Users paste the EXACT DevTools header
names `x-sap-ri=VALUE; x-sap-sec=VALUE` into the SPX session cookie field. The OLD regex
`sap_ri=([^;\s]+)` did NOT match `x-sap-ri=` (the `x-` prefix broke it) → extraction returned
`{}` → `show_secret` called cookies-only → HTTP 401 → phone fetch failed silently for ALL orders.

**Fix — regex MUST include optional `x-` prefix:**
```python
("x-sap-ri", r'(?:x-)?sap_ri=([^;\s]+)'),
("x-sap-sec", r'(?:x-)?sap_sec=([^;\s]+)'),
```
This matches BOTH `sap_ri=` (legacy) and `x-sap-ri=` (DevTools copy-paste). The output key
stays `x-sap-ri` / `x-sap-sec`, so the `fetch_spx_phone()` header-injection code is unchanged.

**Verify after any deploy:** `_extract_sap_headers("session=x; x-sap-ri=ABC; x-sap-sec=DEF")`
must return `{"x-sap-ri": "ABC", "x-sap-sec": "DEF"}`. If it returns `{}`, the regex is wrong
and phone fetch will 401.

## Troubleshooting

### Phone fetch returns None or 401

1. **Check server logs:** Look for `[SPX-PHONE]` log lines showing the `show_secret` response
2. **If HTTP 401:** SPX requires SAP headers (x-sap-ri, x-sap-sec) — move to Pilihan B or C
3. **If retcode != 0:** Possibly invalid entity_id or expired session
4. **If retcode=0 but real_message is null:** SPX limitation — this order's phone cannot be revealed via API (80-90% of orders)

### Testing Approach

1. Deploy `webhook_listener.py` only (Kudu VFS PUT, then restart app)
2. Trigger `POST /api/spx/sync` from dashboard
3. Wait for sync to finish Phase 1 (order fetch) then Phase 2 (phone fetch)
4. Check sync-progress errors array for any SPX_SESSION_EXPIRED or other errors
5. Check DB: `SELECT COUNT(*) FROM spx_self_collection_orders WHERE recipient_phone IS NOT NULL;`

## Key Differences: Order List vs show_secret Auth

| Endpoint | URL | Method | Auth Needed | SAP Headers? |
|----------|-----|--------|-------------|--------------|
| Order List | `/sp-api/point/order/collection/list` | GET | Cookies only | ❌ Not required |
| show_secret | `/sp-api/order/show_secret` | POST | Cookies + ? | ❓ May be required (TBD) |

The order list endpoint works with just session cookies + standard HTTP headers. The show_secret endpoint is more restrictive and may require the SAP security headers.
