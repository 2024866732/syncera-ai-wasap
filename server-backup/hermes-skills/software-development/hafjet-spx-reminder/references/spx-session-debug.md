# SPX Session Debugging Protocol

## Diagnosis Steps When Session Status Returns 401

1. **Check cookie format:** Backend stores whatever string is sent as `{"cookies": "<string>"}` in `spx_session` table. Users must paste the **full Cookie header from DevTools → Network tab → Request Headers** (NOT from Application tab which may miss HttpOnly cookies like CSRF tokens).

2. **Test with lightweight call:** `fetch_spx_order_list(cookies, pageno=1, count=1)` — if this returns data, session is valid.

3. **CSRF token hypothesis:** SPX API may require both `session_token` AND `csrf_token` cookies. Check DevTools Application tab for all cookies under `sp.spx.shopee.com.my`.

4. **Cookie expiration:** SPX sessions expire after ~24h. Re-login to SPX portal.

## Common Error Patterns

| Error | Likely Cause | Fix |
|-------|-------------|-----|
| `SPX_SESSION_EXPIRED` | Cookie expired or invalid | Re-paste from DevTools |
| `401 on /api/spx/session-status` | Backend JWT auth failed (not SPX auth) | Check `Authorization: Bearer <token>` |
| `SPX_SESSION_EXPIRED` returned from fetch | SPX API returned 401 | Re-login to spx.shopee.com.my |
| Status says active but sync returns 0 | Wrong cookies (different account/branch) | Verify cookies match the SPX portal that has orders |

## Cookie Capture Guide (for Dashboard Users)

1. Log in to https://sp.spx.shopee.com.my/ in Chrome/Firefox
2. Open DevTools → Network tab
3. Click any request to `sp-api/` (or refresh the orders page)
4. Find the Request Headers section → copy the entire `Cookie:` value
5. Paste into the SPX Session textarea in dashboard
6. Click "Save & Test Connection"
7. Expected: ✅ SPX Session Active — N orders found

## SAP Headers for show_secret (NOT CSRF)

**Critical update (Jul 2026):** The initial `X-CSRF-Token` hypothesis was WRONG. The `show_secret` endpoint uses SAP security headers (`x-sap-ri`, `x-sap-sec`) which are **dynamically generated by JavaScript** — they are NOT cookies and cannot be extracted from `document.cookie` or DevTools Application tab.

### What Changed

| Before (WRONG) | After (Correct) |
|---|---|
| `show_secret` requires `X-CSRF-Token` header | Requires `x-sap-ri` + `x-sap-sec` SAP headers |
| CSRF token from cookie → echo as header | SAP headers generated by JS client-side |
| Extract `csrftoken` from cookie string | Cannot extract — not in cookies |
| CSRF discovery via Application tab | SAP headers via Network tab request headers |

### Diagnosis Steps

If `GET /api/spx/session-status` returns `active: true` but `fetch_spx_phone()` always returns `None` or `401`:

1. **Check if SAP headers are missing:**
   - Verify `_extract_sap_headers(cookies)` returns `{}`
   - This is EXPECTED — SAP headers are NOT in cookies
   - Current code falls back to cookies-only (no SAP headers)

2. **Check if the request reached SPX:**
   - Look for `[SPX-PHONE]` or `[SPX-DEBUG]` logs showing the `show_secret` response
   - If HTTP 401 → SAP headers required (move to Pilihan B or C)
   - If `retcode != 0` → other issue (invalid entity_id, expired session)

3. **Test with actual SAP headers from portal:**
   - From SPX portal DevTools → Network → click `show_secret` request
   - Copy `x-sap-ri` and `x-sap-sec` values
   - Temporarily inject into code:
   ```python
   headers["x-sap-ri"] = "<value_from_network_tab>"
   headers["x-sap-sec"] = "<value_from_network_tab>"
   ```
   - If this returns `retcode: 0`, SAP headers are the key (Pilihan C)

### Cookie Format Pitfall

Users often open the cookies from **Application → Storage → Cookies** (browser tab) and copy the value column. This loses:
- **HttpOnly cookies** — these are invisible in Application tab but ARE sent in Network tab headers
- **Cookie ordering** — SPX may depend on specific ordering

**Correct capture method:**
1. DevTools → **Network** tab (NOT Application tab)
2. Find any XHR request to `sp-api/*`
3. Click → **Headers** → **Request Headers** section
4. Find the **`Cookie:`** header line — copy everything after `Cookie: ` (it's one long string)
5. Paste exactly that into the dashboard textarea

## Fallback: Phone from CSV Import

If `show_secret` consistently fails for all orders (~80-90% failure rate observed for phone-revealable orders via API), phones may only be retrievable via **CSV export** from the SPX portal. See CSV import endpoint `/api/spx/import-csv` which accepts SPX-exported CSV with unmasked phone column.
